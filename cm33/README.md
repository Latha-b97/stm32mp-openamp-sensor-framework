# CM33 Projects

## OpenAMP_TTY_echo

### Purpose:
Minimal OpenAMP bring-up and validation project.This is an example project from the STM32Cube

### Description:
This project demonstrates the most basic CM33 ↔ Linux communication using OpenAMP RPMsg TTY.
The CM33 firmware echoes data received from Linux back over /dev/ttyRPMSGx.

  Note:
    - No periodic message generation
    - No message queue or sequencing
    - Focused solely on basic connectivity and debugging

### Key concepts:
OpenAMP initialization on CM33
RPMsg TTY channel creation
Basic message receive/transmit path
Linux-side testing using standard TTY tools

### Role in the framework:
Foundation project used to verify:
  - OpenAMP is working
  - Remote processor boot is correct
  - RPMsg transport is functional


## OpenAMP_TTY_Periodic_SeqQueue

### Purpose:
Demonstrates periodic message generation with sequencing from CM33 to Linux over OpenAMP RPMsg. Builds on the minimal echo example by adding structured data handling..

### Description:
Builds on OpenAMP_TTY_echo by introducing periodic data transmission and a sequence queue mechanism.
Instead of simple echoing, the CM33 sends structured messages at fixed intervals, store them in a ring buffer, and transmit them reliably to Linux using OpenAMP.

### Key concepts covered:
Periodic sample message generation
Message sequencing using a ring buffer
Helper functions for enqueue/dequeue of messages
Handling back-to-back RPMsg sends
Consumer logic gated

### Role in the framework:
Serves as a stepping stone toward sensor data streaming and flow-control aware designs.


## TMP_CM33_I2C_OPENAMP

### Purpose:
STM32CubeMX configuration reference project. This is a supporting project to generate the code for OpenAMP_Sensor_Node project.

### Description:
This project contains the STM32CubeMX .ioc file used to configure:

- CM33 core
- OpenAMP middleware
- I2C peripheral
- Clocking and system settings

It may include both CM33 and CA35 domains as generated by CubeMX, but it is not intended to be built or flashed.

### Key concepts covered:
CubeMX-generated initialization code
Peripheral configuration source of truth
Regeneration reference for CM33 projects

### Role in the framework:
This is a temporary project mainly to generate the .ioc file and configure the I2C and OpenAMP.
When peripheral or OpenAMP settings change, this project is updated
Relevant generated code is then manually ported into OpenAMP_Sensor_Node


## OpenAMP_Sensor_Node

### Purpose:
Demonstrates CM33 integration with OpenAMP RPMsg and I2C sensor communication (BME280). This project builds on OpenAMP_TTY_Periodic_SeqQueue by adding sensor interaction.

### Description:
Starting from OpenAMP_TTY_Periodic_SeqQueue, this project sets up CM33 ↔ Linux communication and integrates a BME280 sensor using I2C.

It integrates:
1. Project creation: OpenAMP_Sensor_Node with CM33 as remote core and A35 as master.
2. Peripheral and middleware setup via STM32CubeMX / .ioc:
  	- Enable I2C peripheral for BME280
  	- Enable OpenAMP (RPMsg) middleware
 	- Enable basic clocks and GPIOs
  	- Generate HAL and startup code for CM33
3. Data Flow


[BME280]

│ I2C (HAL_I2C_Mem_Read)

▼

[CM33 RAM]

│ struct sensor_msg

▼

[RPMsg buffer]
│

▼

[Linux]


- CM33 reads data from BME280 via I2C  
- Messages are structured and stored in a buffer  
- RPMsg sends the sensor data reliably to Linux

### Key concepts covered (progressively):
v1: TTY + periodic + sequence queue
  	- Basic OpenAMP + RPMsg stack on CM33
  	- TTY-based RPMsg device (/dev/ttyRPMSGx)
  	- Periodic dummy message generation
  	- Sequence queue with ring buffer for reliable delivery
  	- Validates CM33 ↔ Linux transport with scheduling, queues, and callbacks

v2: + BME280 sensor integration (currently in progress)
  This is integrating with BME280 sensor. It sends BME280 readings to Linux using TTY.
    	1. STM32CubeMX setup (CM33 + OpenAMP + I2C)
		2. BME280 driver integration (CM33 only) - v2a – CM33 sensor integration (no Linux yet). 
		3. RPMsg data send (CM33 → Linux) - v2b – Sensor data → Linux (still use TTY)

v3: + raw RPMsg endpoint
  - Replaces TTY with custom RPMsg channel (sensor_rpmsg)
  - Allows binary payloads and structured message transfer
  - Linux side can use custom driver or user-space endpoint

v4: + flow control & back-pressure (future)
  - Queue depth management to prevent overflow
  - Dropped sample detection
  - Windowing or ACK/NACK for reliable streaming
  - Linux slow-reader protection

v5: + control messages (future)
  - Bidirectional RPMsg: Linux → CM33 commands
  	- Start/stop sampling
  	- Change rate
  	- Calibration trigger
  - CM33 → Linux continues structured sensor data streaming
  - Full RPMsg protocol with control + data channels

### Role in the framework:
This project evolves through multiple versions (v2 → v5) and represents the ensor node firmware.
